# 서비스 개요 문서

## 서비스 설명

취준생/이직자가 여러 회사에 지원한 현황을 한 곳에서 관리하는 서비스.
노션/엑셀로 직접 만들어 쓰던 지원 관리를 취준에 특화된 형태로 제공하며,
지금 어떤 회사가 어느 단계인지, 다음 면접이 언제인지, 합격·불합격 패턴이 어떤지를 한눈에 확인할 수 있음.

---

## 타겟 유저

- 1순위 — 개발자 취준생 (직접 타겟, 베타 테스트 즉시 가능)
- 2순위 — 전직군 취준생 (매년 수십만 명 신규 공급)
- 3순위 — 이직 준비 중인 직장인 (지원 횟수는 적지만 꼼꼼한 관리 니즈 강함)

---

## 핵심 차별점

경쟁 서비스(잡플래닛·자소설닷컴 등)는 채용 공고 탐색이나 자소서 작성 중심이라
전형 단계 파이프라인 관리와 플랫폼 무관 통합 관리가 부재한 공백 지대가 존재함.

- 자소서 작성 도구 X, 지원 현황 파이프라인 관리 O
- 플랫폼 무관하게 모든 지원 통합 관리
- 면접 일정 카카오 알림 (나에게 보내기)
- 합격/불합격 패턴 분석 (Phase 2)
- 취준 타임라인 리포트 공유 + 바이럴 (Phase 3)

## 기술 스택

**백엔드**

```
├─ Java 21
├─ Spring Boot 3.4+
├─ Spring Security (JWT 인증)
├─ Spring Data JPA
├─ MySQL 8.0 (Docker 컨테이너)
├─ Spring Boot Actuator    (헬스체크 및 모니터링 기반)
├─ Springdoc OpenAPI       (Swagger UI 자동 생성)
├─ Spring Scheduler        (@Scheduled, 알림 트리거)
└─ Gradle
```

**프론트엔드**

```
├─ React 19
├─ JavaScript
├─ Zustand                 (전역 상태 관리)
├─ FullCalendar            (면접·마감일 캘린더 UI)
├─ PWA                     (manifest + Service Worker)
├─ Axios                   (HTTP 클라이언트)
├─ lucide-react            (SVG 아이콘)
└─ Pretendard              (웹폰트, CDN)
```

**인프라**

```
├─ AWS EC2 (t3.micro)      (프론트/백엔드/MySQL 올인원)
├─ MySQL 8.0               (Docker 컨테이너로 EC2 내 실행)
├─ Nginx                   (리버스 프록시 + HTTPS, Let's Encrypt)
├─ Docker
├─ Docker Compose          (로컬·운영 환경 통일)
├─ Docker Hub              (이미지 레지스트리)
├─ Flyway                  (DB 스키마 버전 관리)
├─ GitHub Actions          (CI/CD 자동화 — Checkstyle + Test + MySQL 마이그레이션 검증)
└─ DuckDNS                 (무료 도메인, jscope.duckdns.org)
```

**외부 연동**

```
├─ 카카오 소셜 로그인
└─ 카카오 나에게 보내기 API (D-7, D-3, D-1, D-Day 트리거)
```

**코드 품질**

```
└─ CodeRabbit              (AI 코드 리뷰)
```

**추후 도입 예정**

```
├─ Redis                   (알림 큐 관리, DB 부하 분산)
├─ Blue-Green 배포         (무중단 배포, 유저 확보 후)
├─ Prometheus + Grafana    (서비스 모니터링, Actuator 기반)
└─ React Native            (PWA 검증 후 모바일 앱 전환)
```

## 알려진 한계와 보완 과제

### 구조적 한계 (수용)
- **리텐션이 취준 기간에 묶임** — 취업하면 앱을 쓸 이유가 없음. 충성 유저가 생겼다 사라지는 사이클 반복. 이직 시 재방문을 유도하는 구조가 없으면 장기 리텐션 확보 어려움.
- **합격자 데이터 편향** — Phase 3 리포트는 합격자만 공유함. 탈락 패턴 데이터는 구조적으로 쌓이지 않음. "합격자 전형 여정 특화"로 포지셔닝하여 수용.

### 보완이 필요한 과제
- **입력 피로** — 지원할 때마다 히스토리를 직접 입력해야 함. 귀찮으면 이탈. Phase 2 인사이트가 의미있으려면 데이터가 쌓여야 하는데, 쌓이기 전에 이탈하는 사람이 많을 수 있음. → Phase 2 넛지(미입력 건 알림)가 핵심 대응 수단.
- **바이럴 발화점이 적음** — Phase 3 리포트 바이럴은 합격자 수에 의존. 초기 유저가 적으면 합격자 수도 적어 루프가 느리게 돎. → Phase 2로 유저를 먼저 모으는 것이 선행 조건.
- **취준 완료 후 재방문 이유 없음** — 이직 시 재사용 가능하지만 그때까지 앱을 기억할지 불확실. → 장기적으로 이직자 타겟 기능 또는 합격 후기 아카이브가 재방문 동기가 될 수 있음.
